# Agent Instructions

This repository is a lightweight Flask web app for a Physics Bachillerato study platform. Any AI coding agent working here must keep the project understandable, small, and safe for a non-expert maintainer.

## Required Reading

Before implementing changes, read:

- `AGENTS.md`
- `docs/context/01-project-overview.md`
- `docs/context/02-architecture.md`
- `docs/context/03-code-standards.md`
- `docs/context/04-ai-workflow-rules.md`
- `docs/context/05-ui-context.md`
- `docs/context/06-progress-tracker.md`

For feature work, also read the relevant spec in `docs/context/feature-specs/`.

For exercise content work, also read `docs/exercise-bank-format.md` and
`docs/exercise-workflow.md`. For deployment questions, read `docs/deployment.md`.

## Working Rules

- Work on one feature unit at a time.
- Never make broad unrelated changes.
- Never change architecture without explicit approval.
- Never rewrite Git history.
- Never force push.
- Keep Render compatibility.
- Keep `gunicorn app:app` working.
- Keep Flask as the web framework.
- Keep Jinja templates.
- Keep JSON content unless a dedicated spec approves a data-layer change.
- Keep the existing Flask-SQLAlchemy models; adding tables or columns needs
  explicit approval because there are no migrations.
- First-year exercise banks live under `content/exercises/1bach/tN/` as a
  `_topic.json` manifest plus ordered block files. Add new exercises to the
  corresponding block file.
- The exercise JSON files are the only source of truth for every topic
  (T0-T6). Edit them directly. The old bank generators live in
  `scripts/archive/` and must not be run with `--write`; the
  `referencia-ejercicios-tN.md` tables are a historical overview only.
- Keep the project understandable for a non-expert maintainer.
- Prefer small branches and pull requests.

The 2.º Bach induction fixture (4 exercises, no status) is stored but excluded

is generated by `scripts/build_exercise_index.py` (489 exercises); do not edit

Status rules (decided 2026-11-22):

- `draft` is an internal editorial marker for the maintainer and AI agents:
  "not yet reviewed by the teacher". It is not a visibility switch.
- Students see `draft` exercises. `load_exercise_catalogue()` in `app.py` hides
  only `retired`. Do not add draft filtering unless the user asks for it.
- Retire an exercise by setting `status: retired`; never delete it or reuse its
  ID, because attempts are keyed by exercise ID and version.

Provenance: every exercise has an `origin` object (validated by
`scripts/validate_exercises.py`):

- `kind`: `original_teacher_bank`, `adapted_from_pau` or `official_pau`.
  Every 1.º exercise is currently `original_teacher_bank`.
- `reference`: always present; `null` for own exercises, required for PAU kinds.
- `source`: required; the spec, prompt or review that produced the exercise.
- Optional: `batch` (T0 work batch, e.g. `exercise_bank_t0_v4_spec`) and
  `adaptation_note`.

Full field reference: `docs/exercise-bank-format.md`.

Generators and migration scripts:

- The bank generators (`build_t0_v4_bank.py`, `build_t3_t6_exercise_banks.py`)
  are archived in `scripts/archive/`. Do not run them with `--write`; edit the
  block files directly.
- `scripts/migrate_compact_exercises.py` (T0-T2 compact migration) is read-only
  by default and writes only with `--write`.
- After any exercise change, run `scripts/validate_exercises.py`, the topic
  validators that exist (`validate_t0_v4_bank.py`, `validate_t0_v4_math.py`,
  `validate_t1_math.py`), `scripts/build_exercise_index.py`, and pytest.

Physics and grading conventions (decided 2026-11-22):

- Use g = 9,81 m/s² in all statements, solutions and expected values. Lessons
  and banks T0-T6 were unified to 9,81 (PR #6); do not reintroduce 10 or 9,8.
- The numeric grader compares only the value against `tolerance` (or
  `accepted_forms`). It does not check units or significant figures, and that
  is intentional. `significant_figures` and `unit` in a numeric field are
  metadata the grader ignores. When the unit itself must be graded, add a separate
  `unit_expression` field.

## Before Editing

Before editing files:

- Restate the task scope.
- Summarize the plan.
- List the files expected to change.
- Identify any risky or broad changes that need approval.

## During Editing

- Keep changes focused.
- Do not mix product changes, visual redesign, architecture changes, and documentation cleanup unless the task explicitly asks for it.
- Do not change `app.py`, `templates/`, `static/`, `content/`, or dependencies during documentation-only tasks.
- If code changes are made, run tests.
- Preserve Render deployment assumptions.

## After Editing

After completing a unit:

- Summarize what changed.
- Summarize validation results.
- Update `docs/context/06-progress-tracker.md`.
- Report files changed.
- Report any known risks or follow-up work.

## Validation Expectations

- For documentation-only changes, run `git status`.
- If the local environment exists, run pytest when practical.
- For code changes, run the smoke tests and any relevant Flask import/test-client checks.
